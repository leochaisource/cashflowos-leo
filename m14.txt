feat(telegram): send one client's brief to that client's group

Adding the bot to a group was already possible; routing a SINGLE client's brief
there was not. The only existing knob, TELEGRAM_TEAM_CHAT_IDS, is global — point
it at a client group and every other client's spend, leads and revenue lands in
it too. That is the mistake this change makes impossible.

- Per-client destinations: briefChatIdEnvs names env vars (not ids, so a group
  id never enters git), most specific first — the client's own group, else the
  agency team list, else the owner's private chat. Verified: with
  CLAUDE_MALAYSIA_GROUP_CHAT_ID set, Claude Malaysia's brief goes to the group
  and Dianna's still goes to the owner.
- /chatid replies with the id of wherever it was sent, because "add the bot,
  send /chatid, paste the number" is the only humane way to learn a group id.

Two things that would have gone wrong in a real group:

1. An unauthorised sender got a public "Not authorized. Your Telegram id is
   12345" reply. In a client's group that announces itself to everyone, prints a
   member's Telegram id, and makes the bot look broken. It now refuses silently
   in groups and keeps the helpful message for private chats.
2. Telegram privacy mode can be switched off, and then every message in the
   group reaches the tool loop and spends model credit answering conversations
   nobody addressed to us. In groups the bot now answers only commands,
   @mentions, replies to itself, and photos.

sendMessage returns whether it actually landed, and the brief records delivered
vs failed per destination. A bot removed from a group used to fail into a
console log while the run still reported "sent" — the same silent-degradation
shape that hid the Adyntel outage for a week.
